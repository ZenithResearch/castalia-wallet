# Shared portable Wallet identities

Core 0.3.0 adds the closed `castalia.wallet-identities.v1` descriptor section under `sections.walletIdentities`. The synthetic `section.json` is the cross-client fixture, not proof of account ownership. This is the implemented public-reference subset; the broader proposed CWS-001 custody and recovery profile is not claimed.

The exact section fields are `schema`, integer `version:1`, `ownerMemberKey` (current Wallet's 64 lowercase hex public key), `authority:"descriptor-only"`, and `accounts` (maximum100). Each account has exactly `accountId`, `kind`, `label`, `identifier`, `server`. IDs are canonical lowercase non-nil UUIDs, preserved from prior app references. Labels are nonempty and at most100 UTF-8 bytes, identifiers320, servers500. Controls and bidi formatting characters reject. Account ordering normalizes ascending accountId.

Kinds: `matrix` requires an `@local:server` identifier and HTTPS homeserver origin, no credentials/query/fragment; `nostr` requires64 lowercase hex and an empty server or wss relay URL without credentials/query/fragment. `github` and `x` use immutable positive decimal provider IDs (1–40digits, no leading zero), with empty server; usernames are labels, not stable IDs. No OAuth or provider verification is enabled. The schema rejects other kinds and unknown fields, including tokens, keys or verified-control assertions. Tailscale remains application/network state and is not migrated.

Native commands are `wallet_identities {}` (section directly), `chain_accounts {}` (existing read-only derived public section), and `prepare_wallet_identities {identities,expected_revision}`. Preparation returns the existing candidate/commit/confirm preview with `wallet_identities`, without durable writes. All require unlock. Full-section replacement is an explicit edit; host persistence remains atomic CAS. Import uses an additive merge: identical records are idempotent, same ID with different fields or same kind+identifier under different IDs rejects without mutation. Labels never merge accounts.

Files with this section use `castalia.castaway-contents.v2`, integer version2, and an authenticated `castalia.castaway.v2` envelope with `contentsSchema:"castalia.castaway-contents.v2"`. Section identity/profile, memberships and root-derived chain descriptors retain their previous meanings. V2 requires walletIdentities, including an empty collection after explicit removal; v1 never accepts it. Files without the section keep frozen v1 identifiers. Readers accept both and bind outer/inner versions. Old software rejects v2; never strip the section to make an old reader accept a file. Encryption/KDF profiles and `.castalia-recovery` are unchanged.

Importing v1 into a Wallet with newer identity records preserves those records. Existing profile/proof import semantics and independent issuer trust checks remain in effect. Account descriptions do not authenticate, grant permissions, revive origin approvals, prove control, or recover private Nostr keys/Matrix sessions. Native app-registry migration must show the records for explicit confirmation, preserve IDs, retain original files and unrelated Tailscale records, and leave original data intact on cancellation/conflict/stale revision/persistence failure. New export coverage must be verified by opening the actual Castaway file in another supported consumer; local save is not a backup claim.

The shared Web/extension primitive `validateCastawayDescriptors(contents)` checks the complete public-data allowlist, holder binding, root-derived account descriptors, and membership-proof structure. It does not authenticate issuers or activate membership. Native import and Web application verification still require independently configured issuer trust before using a proof; Chrome retains public proofs as unverified portable data and never installs them into active membership through this identity import. V2 Web ciphertext paths enforce the same strict descriptor validation, while historical v1 Web byte formats remain compatible.
