## MV3 Service Worker Messaging Constraints (Key Reference)
- Service workers are **ephemeral** (terminated after ~30s idle; woken on events). No long-running state in globals across wakes except via storage.
- `chrome.runtime.sendMessage` / `onMessage` works between popup (extension page) and SW.
  - From popup: `chrome.runtime.sendMessage(msg).then(response => ...)` (async)
  - From SW: `chrome.runtime.sendMessage(msg)` (fire-and-forget to any open listeners; no tab targeting needed for popups)
- Sender identification: In SW listener, `sender.tab` is `undefined` for popup/extension pages (vs. content scripts). Use `sender.id === chrome.runtime.id && !sender.tab` to confirm internal popup origin.
- **No easy "direct port to specific popup"**: `chrome.runtime.connect()` works (long-lived Port), but requires the popup to initiate the connect. SW can maintain a list of connected ports and `.postMessage()` to them. More boilerplate than needed for state.
- Broadcast nature: `sendMessage` reaches all listeners (popup + any future options pages). Filter by message shape.
- Storage events are **first-class** for reactivity: `chrome.storage.onChanged` fires in **all** contexts that have the storage open (including popup) when SW (or anyone) writes to `storage.session`.
- Polling fallback always works: popup can call `getState` via messaging on open/focus/interval.
- Common robust patterns (in priority order for this use case):
  1. **Storage listener (recommended primary)**: Popup subscribes to `chrome.storage.onChanged`. Zero extra SW push code. Works across SW restarts.
  2. **Explicit sendMessage push from SW** (after mutations): Simple, but requires popup listener + race handling on popup open.
  3. **Port connection**: For higher-fidelity bidirectional if future needs (e.g. streaming).
  4. **Pure polling**: On every popup open + visibilitychange.
- Other gotchas:
  - Messages can be lost if SW is suspended during send (rare with storage fallback).
  - Extension reload (chrome://extensions) kills SW + clears some state; storage.session is cleared by browser on full extension reload in many cases.
  - Firefox MV3 differences (not yet in scope; this extension targets Chrome first per Option B).
  - No extra permissions required beyond "storage" for onChanged/sendMessage/onMessage.

## Recommended Architecture for Reverse Direction (Post T1.3)
Assume T1.3 has established a clean messaging contract (e.g. types in bridge.ts or a new `messaging.ts`, handlers for popup actions that call into `sessionState.*`, and a `getState` query).

### Option A (Preferred — Minimal Code, Maximum Reliability): Storage Events + Direct Reads
Popup can **directly** read `chrome.storage.session` (same as SW). No messaging needed for reads.

**Sketch for popup.ts (to be implemented in T1.4 or popup-UI task):**
```ts
import type { SessionWalletState } from './state/session-state.js'; // or shared types

const STORAGE_KEY = 'castalia-session-state'; // consider exporting from session-state

async function loadState(): Promise<SessionWalletState> {
  const result = await chrome.storage.session.get(STORAGE_KEY);
  return result[STORAGE_KEY] ?? getDefaultState(); // or call a getState message
}

function updateUI(state: SessionWalletState) {
  // render setupComplete, unlocked badge, approvedOrigins list, publicKey, etc.
  // show/hide screens based on state
}

async function initPopup() {
  const initial = await loadState();
  updateUI(initial);

  // Reactive updates (the "push" from storage changes made by SW)
  chrome.storage.onChanged.addListener((changes, area) => {
    if (area === 'session' && changes[STORAGE_KEY]) {
      const newState = changes[STORAGE_KEY].newValue as SessionWalletState;
      updateUI(newState);
    }
  });

  // Optional: visibility/focus refresh as safety
  document.addEventListener('visibilitychange', async () => {
    if (!document.hidden) {
      const fresh = await loadState();
      updateUI(fresh);
    }
  });
}

document.addEventListener('DOMContentLoaded', initPopup);
```

**In SW (mutations from T1.3 handlers):**
After `await sessionState.setup()`, `await sessionState.approveOrigin(...)`, etc., the storage write already happened inside the manager. The popup listener above will fire automatically. **No extra sendMessage required.**

This is the cleanest seam.

### Option B: Explicit Push via sendMessage (if storage listener not desired)
Extend T1.3's SW onMessage handler:

```ts
// After any state mutation in the handler:
const latestState = await sessionState.getState();
chrome.runtime.sendMessage({
  type: 'castalia:state-update',
  payload: latestState
}).catch(() => {}); // ignore "no listener" if popup closed
```

In popup (add to the onMessage listener from T1.3, or separate):
```ts
chrome.runtime.onMessage.addListener((msg, sender, sendResponse) => {
  if (msg.type === 'castalia:state-update') {
    updateUI(msg.payload);
    sendResponse({ ok: true }); // if needed
  }
  // ... existing T1.3 handlers
});
```

**Hybrid**: Use storage listener as primary + sendMessage as "hey, refresh now" signal (for cases where storage area doesn't fire in some edge MV3 wakes).

### Fallback: Polling
If neither above, popup on init + every 2s (while visible):
```ts
const state = await chrome.runtime.sendMessage({ type: 'castalia:get-state' });
// T1.3 must support this query
updateUI(state);
```

## Required Changes to Service-Worker Startup (clearForReload Call)
**This is mandatory for the per-session safety contract** and must land early (can be done independently of full T1.4 messaging push).

**Seam / Sketch (add to `src/service-worker.ts`):**

1. Add import at top:
   ```ts
   import { sessionState } from './state/session-state.js';
   ```

2. Add lifecycle listeners (place after imports, before any other chrome usage; top-level execution is fine in MV3 modules):
   ```ts
   // Service worker lifecycle — enforce fresh session on every load/reload
   chrome.runtime.onInstalled.addListener(async (details) => {
     console.log('[Castalia SW] onInstalled reason:', details.reason);
     if (details.reason === 'install' || details.reason === 'update') {
       await sessionState.clearForReload();
     }
   });

   chrome.runtime.onStartup.addListener(async () => {
     console.log('[Castalia SW] onStartup — clearing session state');
     await sessionState.clearForReload();
   });

   // Optional but recommended for robustness:
   // chrome.runtime.onSuspend.addListener(() => {
   //   console.log('[Castalia SW] onSuspend');
   // });
   ```

**Why these events?**
- `onInstalled`: Fires on first install, update, or reload of extension (chrome://extensions reload button).
- `onStartup`: Fires when browser starts (extension auto-starts).
- Ensures `clearForReload()` runs before any page requests or popup opens in the new "session".
- In-memory keys are nulled; storage.session is wiped + reset to defaults.
- After this call, `getState()` returns clean `{ setupComplete: false, ... }` until explicit `setup()`.

**Integration note**: Once added, the legacy `ExtensionWalletState` construction in `handleProviderRequest` / tests will need to evolve to:
```ts
const s = await sessionState.getState();
const keyPair = getInMemoryKeyPair(); // from session-state helpers
const approvedSet = new Set(s.approvedOrigins);
// then build ExtensionWalletState or refactor to use SessionWalletState directly
```

**Timing**: This can (and should) be added as soon as T1.2 state model is stable — even before full T1.3 messaging. It is a small, isolated, high-value change.

## Seams & Contracts (for T1.3 + T1.4 Implementers)
- **Shared types**: Move `SessionWalletState` (and `STORAGE_KEY`) to a common place (e.g. `src/types.ts` or re-export from state). Popup and SW must agree on the shape for get-state responses and storage.
- **Messaging contract (T1.3 owns definition)**:
  - Requests from popup: `{ type: 'castalia:popup-action', action: 'setup' | 'unlock' | ... , payload? }`
  - Responses: `{ ok: boolean, result?, error? }`
  - Add `get-state` query if not present.
  - State-update push (optional for Option B): `{ type: 'castalia:state-update', payload: SessionWalletState }`
- **State access**:
  - Popup: Prefer direct storage read + onChanged for UI.
  - SW: Always go through `sessionState` (never bypass for mutations).
  - Future: Thin read-only facade in popup context if we want to hide storage key.
- **Error / failure modes**:
  - Popup must handle "not set up", "locked", empty approvals gracefully (per Option B plan).
  - On SW wake after clear: page calls will get proper "wallet setup required" errors.
- **Build / dist**: After changes, `npm run build --workspace @castalia-wallet/chrome-extension` (from monorepo root) to update dist/.
- **Tests**: Extend `service-worker.test.ts` and add popup-messaging tests once contract stable. Test `clearForReload` explicitly (it is currently untested in unit suite).
