# Canonical Wallet packages

Linux x86_64 Buildkite is the canonical builder, using Rust 1.85.1, Node 20.20.0, wasm-pack 0.14.0, wasm-bindgen 0.2.127 and Binaryen 117. Official binding/optimizer archives and extracted binaries are checksum-pinned in the bootstrap and `canonical-tools.json`. Their versions and hashes are recorded with the lockfile hashes. Rust paths are mapped to stable logical locations; incremental output is disabled. wasm-pack uses the verified PATH binaries in `no-install` mode, preventing cache installation fallback. Other platform builds remain useful development builds, not canonical distribution evidence.

The hosted reproduction gate makes two clean checkouts at the exact requested commit in different directories, installs from the existing npm lock and compiles each with independent target directories. It compares complete trees including manifests, source notices, licenses and every bundled file, and compares that result to the delivered package. No source package pin changes are involved. The filesystem candidate remains unchanged.

## Earlier macOS / Linux difference

At parent d14a2d3, local tree `3474cec3d5a2fe5990e77fd11bd0985bce6379bf1a11abaf7758ad1314033708` and Buildkite #13 tree `554463b15e80cbab4c477ded7f207e6e340e8d77d8b30679b4efdc953a11bf9c` differed only in `dist/service-worker.js`, through embedded WASM. Local WASM: 1,189,656 bytes, SHA-256 `eb5e6e73ec26b2348f89d7a576ea067197ebe49b96d34bb633852a3813159245`. Hosted WASM: 1,192,021 bytes, SHA-256 `4d5240fc89be82ed4b3264f5ba4266b86a50e4c091a8fb4c2d318c8ffdf59c9c` (see the preserved binary inventory for the authoritative digest). The code/data sections differed, not only metadata. The binding producer was locally reported as 0.2.127 and hosted as 0.2.127 (a579ee62b); the former builder also permitted uncontrolled binary/cache selection and absolute source paths. Those are reproducibility inputs now controlled, not proof of a single historical cause. Canonical reproducibility does not require macOS and Linux bytes to match. Chrome acceptance must use the exact downloaded canonical package.

Required GitHub checks, installed-runtime retirement and production rollout remain separate decisions. This CI change grants no trust to an issuer and does not alter signing, custody or recovery contracts.

## Upgrade and independent endpoint acceptance

Run `scripts/smoke-extension-upgrade.mts` with the downloaded `CASTALIA_EXTENSION_DIRECTORY` and `CASTALIA_UPGRADE_BASELINE` from the preserved main #8 archive. The script checks the known baseline digest. First use its production-shaped package; separately use its archived issuer fixture with `CASTALIA_UPGRADE_LEGACY=1`. Each journey owns a disposable profile and a stable unpacked path; package files are never modified. The legacy fixture requires free loopback port 3002 and fails if occupied, without replacing a preview. Recovery material stays in memory or the disposable profile and is not included in reports.

The Linux issuer lane uses separate HTTPS hostnames and Ed25519 authorities. Its CA is added only to a newly created browser HOME/NSS database, then deleted with that disposable environment. No host trust store, real profile, certificate bypass flag or `ignoreHTTPSErrors` option is used. It covers host-permission isolation/removal, pending-consent invalidation, wrong issuers/keys/holders, redirects, substituted credentials, untrusted certificates, hostname mismatch and reapproval. Its passing result qualifies these test-CA endpoints only, not real production issuers.

Five existing loaded Chrome journeys remain required on the exact downloaded canonical package, in addition to both upgrade reports. Required GitHub checks are unchanged; all qualification reports must name their source commit and package digest.

The independent-issuer lane approves Chrome’s native host prompts through AT-SPI in its disposable Xvfb session. The helper requires the exact test hostname, Castalia label and visible Allow button; it fails closed on an unrecognized prompt. It does not inject permissions, bypass certificates or change the host trust store. Upgrade acceptance enables developer mode only in the disposable profile, explicitly reloads the stable unpacked extension and waits for the replacement service worker.

Linux qualification downloads the current job’s archive and immutable main #8 archive, checks archive hashes, restores safely and runs all five existing Chrome journeys plus both upgrades with fresh profiles. The archive’s source and tree digest must match the build and reproduction manifest. Each result remains separately logged; the existing operator review block remains in place. Independent-host removal uses Chrome’s supported per-site access UI, because its permissions API cannot remove required content-script permissions. The historical provider-profile lane retains its labelled certificate-bypass fixture; the new two-hostname TLS lane has no certificate bypass.
